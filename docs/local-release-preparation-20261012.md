# Local Release Boundary

## Application And Regression Scope

The release keeps approved-source bounded fact extraction/rendering, the existing authentication/search/generation flow, optional development-only minimum numeric/span/usage diagnostics, staff persistence and UI regressions, and production private-file tracing exclusions.

One-off approval manifests, fixed live-test questions, readiness proofs, request-count budgets and browser submission helpers are not application dependencies. Private execution headers/body markers are rejected rather than silently routed through ordinary chat. Historical S1/S2 evidence remains unchanged; separation is validated offline and does not rerun or retroactively alter those actual results.

## Included Changes

- Whitespace-only repairs in the previously reported HQ pages and six staff/common files. Logic, indentation and line endings are preserved.
- RAG implementation and public regressions: source facts/renderer, support verification, source targeting, prompt qualifier preservation, optional safe diagnostic implementation, and ordinary provider usage callbacks.
- Staff response/history/UI support plumbing stays off unless the existing storage/full-badge opt-ins are explicitly enabled. No opt-in or migration is performed here.
- Existing owner-notice responsive fixes and signup recovery changes/tests are preserved, not reverted.
- The new release-boundary test checks absence of temporary imports/npm scripts and the production tracing exclusions. Minimum diagnostic privacy/unknown-usage tests live in the public RAG regression, not only in an excluded harness test.
- The generic deleted-email-signup SQL draft is included because existing signup regressions load it and the app references its RPC. It contains no actual target account data. It remains a draft, is not moved into migrations or applied, and its schema prerequisite remains an operational limitation.

## Excluded And Preserved

- Environment files, private local-data ledgers/approvals/actual records, development output, credentials and Vercel linking state.
- One-shot execution modules, browser submission/reproduction scripts and their private approval/budget tests.
- Actual-observation response fixture and operational actual-answer/trace investigations, even when they have no API key.
- Account-targeted SQL/runbook edits containing real emails or identifiers, and one-off cleanup SQL drafts.
- Unrelated investigation/deployment-operation documents not needed for this code selection; all remain on disk.

The exact include/exclude list, reasons and hashes are held in the ignored release-separation file manifest. No excluded file is deleted or staged. A clean detached release worktree is used to validate the selection without copying environment/private records.

## Gates And Restrictions

Require main-to-worktree whitespace verification, full verify:poc (including typecheck and production build), public privacy/boundary regressions, and zero private references in emitted production manifests. A full dirty-worktree pass alone is not proof that the selected release subset is complete.

Push/merge remain blocked pending Vercel Git-connection verification. Installing the GitHub App is not proof that a Vercel project is connected. No database changes, paid calls, reindexing, remote settings changes or deployment are authorized by this local preparation.
