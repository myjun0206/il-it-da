# 매뉴얼 파일 형식별 파싱 계약 제안서 (Manual File Format Contract Proposal)

> **이 문서는 제안서입니다.** 실제 파서 구현이나 DB 스키마, 업로드 API 계약을 확정하거나
> 변경하지 않습니다. `tests/fixtures/manual-formats/`의 샘플과 기대 결과(JSON)는 형식별
> 파서를 설계/구현할 때 참고할 수 있는 자료이며, 아직 실제 파서 코드와 연결되어 있지
> 않습니다(별도 테스트에서 구조적 유효성만 검증합니다).

## 1. 지원 범위

| 분류 | 형식 | 비고 |
|---|---|---|
| 지원 대상 | XLSX, XLS, CSV, TXT, MD | 매뉴얼 업로드에서 다뤄야 하는 핵심 형식 |
| 선택 지원 | DOCX | 있으면 좋지만 필수는 아님. 아래 "DOCX 샘플 작성 지침" 참고 |
| 추후 지원 | PDF, 이미지(OCR) | 이번 범위 밖. AI/OpenAI/Vision/OCR을 새로 추가하지 않는다 |

## 2. 기준 매뉴얼 (가상 카페)

`standard.*`와 `variant.*` fixture는 **의미상 완전히 같은 매뉴얼**입니다. category/title/items
내용은 두 세트 사이에서 한 글자도 다르지 않아야 합니다. `variant.*`는 아래 표현(포맷)
차이만 추가로 포함합니다 — 내용 자체를 바꾸지 않습니다.

- CRLF(`\r\n`) 입력에 대한 처리 계약(아래 CRLF 안내 상자 참고)
- 빈 행(줄)
- category/title 앞의(leading) 공백
- 탭 들여쓰기
- 동일한 CSV 행의 반복(중복 행)
- 숫자처럼 보이는 문자열은 본문 내용이나 순번 표시 안에만 등장한다(제목 자체를 숫자로
  바꾸지 않는다 — 숫자 제목 보존은 5.1절의 별도 예시로 다룬다)

> **trailing whitespace 예외**: category/title 뒤(trailing) 공백 trim 계약은 실제로
> 존재하지만, 물리적 줄 끝 공백은 이 저장소의 `git diff --check` 품질 게이트에 걸리므로
> `variant.md`/`variant.txt` 파일에는 커밋하지 않는다. 이 계약은 대신
> `tests/manuals/manual-format-fixtures.test.ts`의 인라인 문자열 리터럴
> (`"출근 후 점검  ".trimEnd()`)로만 검증한다. `variant.csv`는 셀 중간(쉼표 앞)의
> trailing 공백이라 줄 끝 공백이 아니므로 예외적으로 그대로 유지한다.
>
> **CRLF 안내**: 파서는 `\r\n` 입력을 지원해야 하지만, 커밋된 fixture 파일의 물리적
> 줄바꿈이 항상 CRLF라고 가정해서는 안 된다 — Git checkout 시 줄바꿈은 플랫폼/설정
> (autocrlf, `.gitattributes` 등)에 따라 LF로 정규화될 수 있다(예: GitHub Actions의 Linux
> 러너). 그래서 `tests/manuals/manual-format-fixtures.test.ts`는 fixture 파일 자체에
> `\r\n`이 들어있는지 확인하지 않는다. CRLF 처리 자체는 OS/checkout과 무관한 인라인
> 문자열 테스트, 그리고 실제 파서를 직접 호출하는 런타임 테스트
> (`tests/manuals/detect-manual-item.test.ts`, `tests/manuals/parse-excel-table.test.ts`)로
> 검증한다.

브랜드명·실명·연락처 등 실제 정보는 전혀 포함하지 않습니다.

- 카테고리: `오픈 준비`, `위생 관리`
- 제목: `출근 후 점검`, `커피 머신 준비` (오픈 준비) / `손 씻기`, `작업대 청소` (위생 관리)
- 각 제목 본문은 번호(`1-1.`, `1-2.` ...), 주의사항(`주의: ...`), 들여쓰기(탭) 항목을 포함

## 3. 형식별 category / title / content 식별 규칙 (제안)

### 3.1 XLSX / XLS / CSV (표 형식)

- `category`, `title`, `content`에 대응하는 열을 명시적 헤더 키워드(`category`/`카테고리`,
  `title`/`타이틀`/`제목`/`주제`/`소주제`, `content`/`내용`/`본문`/`세부매뉴얼`/`item`/`items`)로
  먼저 찾는다. 헤더를 못 찾으면 "같은 값이 연속으로 반복되는 축"을 category로 보는
  휴리스틱으로 대체한다.
- **병합 셀**: category 열이 첫 행에만 채워지고 아래 행이 비어 있으면, 바로 위 값을
  forward-fill로 이어받는다.
- **가로형(전치) 표**: category/title이 열이 아니라 행 방향으로 나열된 경우, 표를
  전치(transpose)해 같은 규칙을 적용하고 세로형과 동등한 결과를 내야 한다.
- **숫자 셀**: 스프레드시트가 숫자 타입으로 내려주는 셀(예: 제목이 `10`처럼 순수 숫자)은
  문자열로 정규화한다(`String(value)` 후 trim). 값 손실이나 예외가 없어야 한다.
- **공통값/노이즈 열**: 모든 행에서 값이 완전히 같은 열(예: 브랜드명 고정 열)은
  category/title/content 어느 역할로도 선택하지 않는다.
- **빈 행/중복 행**: 모든 셀이 빈 행은 제거한다. 완전히 동일한 행이 반복되면 하나만
  남기고 중복 매뉴얼을 만들지 않는다.
- `content` 셀 안에서 항목(items) 분할 규칙은 3.4절과 동일하다.

### 3.2 TXT (평문)

- **category 경계**: `[카테고리명]` 형태의 단독 줄. 파일 안에 이런 줄이 2개 이상 있어야
  경계로 인정한다(1개뿐이면 오검출 방지를 위해 전체를 "미분류" 하나로 본다).
- **title 경계**: category 블록 안에서 줄 맨 앞이 `N.` 또는 `N)`로 시작하는 줄(마찬가지로
  블록 안에 2개 이상 있어야 인정). 이 숫자는 title의 "순번 표시"일 뿐이며 실제 제목 텍스트는
  그 뒤에 오는 문자열이다.
- **content**: 각 title 줄 다음부터 다음 title/category 줄 전까지의 텍스트 전체.
- ⚠️ **알려진 제약**: title 경계 패턴(`^N.`)은 줄 앞 공백/탭이 있어도 매칭되므로, title
  본문 안에서 같은 패턴(들여쓰기 없는 `N.`)을 항목 구분자로 재사용하면 안 된다. 항목
  구분은 반드시 3.4절의 `N-N.`(하위 번호) 또는 탭 들여쓰기만 사용한다.

### 3.3 MD (마크다운)

- **category 경계**: `#` 또는 `##`(H1/H2) 헤딩 줄. 2개 이상 있어야 인정.
- **title 경계**: `###`~`######`(H3~H6) 헤딩 줄. 같은 category 블록 안에 2개 이상 있어야
  인정. `#`/`##`와 `###`~`######`가 레벨로 구분되므로 TXT와 달리 title 본문 안에 다른
  숫자를 자유롭게 써도 category/title 경계와 충돌하지 않는다.
- **content**: 각 title 헤딩 다음부터 다음 헤딩 전까지의 텍스트 전체.

### 3.4 항목(items) 분할 규칙 — 형식 공통

모든 형식의 `content`(또는 title 본문)는 아래 규칙으로 items 배열로 나뉜다. 이는
XLSX/CSV/TXT/MD가 공유하는 하나의 계약이다.

1. 줄 맨 앞의 단독 번호(`1.`, `2.`, `1)`, `2)` ...)는 새 항목의 시작이다.
2. 줄 맨 앞의 하위 번호(`1-1.`, `1-2.` ...)나 탭/공백 들여쓰기로 시작하는 줄은 "그룹
   트리거"로 취급한다 — 그 줄부터 다음 그룹 트리거(또는 본문 끝) 전까지는 하나의 항목으로
   묶인다. 트리거를 새로 만나면 이전 섹션은 끝나고 새 섹션이 독립적으로 시작된다.
3. 위 두 경계가 전혀 없으면 빈 줄(문단 구분)로 나누고, 그마저 없으면 본문 전체를 항목
   하나로 취급한다. 예외를 던지지 않는다.

### 3.5 빈 줄 / 공백 / CRLF / 숫자 / 하위 번호 / 들여쓰기 — 기대값 표

| 입력 | 기대 동작 |
|---|---|
| 완전히 빈 행/줄 | 제거한다 (category/title/content 어디에도 남지 않는다) |
| category/title 앞뒤 공백 | trim 후 저장한다 (`" 오픈 준비 "` → `"오픈 준비"`). trailing 공백은 물리적 줄 끝 공백이 되는 `variant.md`/`variant.txt`에는 커밋하지 않고, 테스트 내부 문자열 리터럴로만 검증한다(2절 참고) |
| CRLF(`\r\n`) | LF와 동일하게 처리한다 — 줄바꿈 위치만 다를 뿐 내용 손실·중복이 없어야 한다. 단, 커밋된 fixture 파일이 항상 CRLF 바이트를 담고 있다고 가정하지 않는다(Git checkout 시 LF로 정규화될 수 있음). 이 처리 계약은 fixture 파일이 아니라 인라인 문자열/실제 파서 런타임 테스트로 검증한다(2절 CRLF 안내 참고) |
| 숫자 전용 셀/텍스트(예: title이 `"10"`인 경우) | 그대로 문자열로 보존한다 (반올림/서식 변경 없음). 별도 예시는 5.1절 참고 |
| `N-N.` 하위 번호 | 3.4절 규칙대로 앞 항목 내용에 포함되거나 자체 그룹으로 묶인다 (표/텍스트 원문 그대로 유지, 숫자를 지우지 않는다) |
| 탭/공백 들여쓰기 | 항목 구분자로만 동작하고, 실제로 저장되는 텍스트에서는 앞의 들여쓰기 문자를 trim한다 |
| 동일 행 반복(표 형식) | 첫 번째만 남기고 중복 매뉴얼을 만들지 않는다 |

## 4. 잘못된 입력의 실패 기준

파서는 아래 입력에 대해 **예외를 던지지 않고**, "인식된 매뉴얼 없음"(빈 배열 또는 `null`)을
반환해야 한다. 절대 빈/의미 없는 placeholder를 DB에 저장하도록 값을 지어내면 안 된다.

- 빈 workbook/빈 시트, 빈 파일
- 의미 있는 열이 하나뿐인 표(카테고리를 구분할 축이 없는 표)
- 모든 셀/줄이 공백뿐인 입력
- category 또는 title 텍스트가 비어 있는 레코드(해당 레코드만 건너뛴다)

## 5. 형식 간 동일 정규화 계약

**같은 내용은 어떤 파일 형식으로 표현되든, 그리고 표현(포맷)만 지저분해지든, 정확히 같은
정규화 결과**(category/title/items 문자열이 한 글자도 다르지 않음)를 내야 한다. 이 계약은
두 축으로 검증한다.

- **형식 축**: `expected-standard.json`은 `standard.csv`/`standard.txt`/`standard.md` 세
  파일 모두가 만족해야 하는 하나의 기대값이다. `expected-variant.json`은
  `variant.csv`/`variant.txt`/`variant.md` 세 파일이 만족해야 하는 기대값이다.
- **표현 축**: `standard.*`와 `variant.*`는 2절에서 밝힌 대로 의미상 같은 매뉴얼이므로,
  **`expected-variant.json`은 `expected-standard.json`과 deepEqual(완전히 동일)이어야
  한다** — variant의 CRLF/빈 행/공백/탭/중복 행 같은 표현 차이는 정규화 후 결과에
  어떤 흔적도 남기지 않는다는 뜻이다.

항목의 배열 순서와 문자열은 정확히 일치해야 하며, DB id/UUID 등 저장 시점에만 생기는 값은
이 기대값에 포함하지 않는다.

### 5.1 숫자 제목 보존 (별도 예시, 동일성 계약과 분리)

"제목이 순수 숫자 문자열이어도 그대로 보존되어야 한다"는 규칙은 실제 계약이지만,
standard/variant 동일성 fixture에 섞으면 5절의 deepEqual 계약이 깨진다. 그래서 이
규칙은 fixture 파일을 늘리지 않고, 검증 테스트 안에 있는 작은 인라인 예시
(`{ category: "위생 관리", topic: "10", items: [...] }`) 하나로만 별도 확인한다.
이 예시는 standard/variant 동일성과 무관하며, `parseExcelTableGroups`/`parseManualText`를
호출하지 않고 구조(문자열 타입, 비어 있지 않음)만 검사한다.

## 6. DOCX 샘플 작성 지침 (선택 지원)

저장소에는 현재 안전하게 DOCX 바이너리 fixture를 생성하는 기존 스크립트/유틸리티가 없다.
새 패키지나 임의 바이너리 파일을 추가하지 않기 위해, DOCX 샘플은 **아래 지침에 따라 필요할
때 직접(로컬에서) 만들어 사용한다** — 이 저장소에는 커밋하지 않는다.

1. 기준 매뉴얼(2절)의 텍스트를 그대로 사용해 워드 프로세서(Word, 한글, LibreOffice Writer
   등)에서 새 문서를 만든다.
2. category는 제목 스타일(예: "제목 1"/Heading 1), title은 그보다 한 단계 낮은 제목 스타일
   (예: "제목 2"/Heading 2)로 지정한다 — MD의 `#`/`###` 레벨 구분과 동일한 개념이다.
3. 본문(1-1./1-2./주의/들여쓰기)은 일반 문단으로 그대로 입력한다. 자동 글머리 기호/번호
   매기기 기능은 끄고 입력한 텍스트("1-1. ...")가 그대로 보이게 한다.
4. `.docx`로 저장한다. `lib/manuals/extract-docx-text.ts`는 `/word/document.xml`만 읽으므로,
   표/이미지/각주 등 복잡한 구조 없이 순수 텍스트 문단 + 제목 스타일만 사용해야 한다.
5. 실제 파서를 구현할 때는 제목 스타일 레벨(Heading 1/2)을 category/title 경계로 매핑하는
   방식을 3.3절(MD)과 동일한 개념으로 설계하는 것을 제안한다.

## 7. 참고 (기존 구현과의 관계)

이 문서와 `tests/fixtures/manual-formats/`의 기대값은 현재 저장소의
`lib/manuals/parse-excel-table.ts`(XLSX/XLS/CSV)와 `lib/manuals/analyze-manual-with-ai.ts`
(TXT/MD)가 실제로 만들어내는 결과를 참고해 작성했다(둘 다 로컬 규칙 기반이며 AI/OpenAI
호출이 없다). 다만 이 문서 자체는 그 구현을 확정하거나 대체하는 것이 아니라, 형식이
늘어나거나 규칙을 다듬을 때 참고할 수 있는 제안서다.
