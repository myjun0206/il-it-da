# Supabase Single Session 설정

Supabase Pro의 사용자당 단일 세션 정책은 앱 코드나 SQL migration이 아니라 프로젝트 Auth 설정에서 활성화합니다.

1. Supabase Dashboard에서 대상 프로젝트를 선택합니다.
2. **Authentication → Sessions**로 이동합니다.
3. **Single session per user**를 켜고 변경사항을 저장합니다.

이 정책은 가장 최근 로그인 세션만 유지합니다. 기존 세션을 즉시 푸시 로그아웃하지 않으며, 기존 세션이 다음에 access token을 refresh할 때 폐기가 감지됩니다. 기본 JWT 만료 시간이 길면 이전 기기에서 만료 안내가 보이기까지 그만큼 지연될 수 있습니다. Supabase는 JWT 만료 시간을 5분 미만으로 낮추는 것을 권장하지 않습니다.

앱은 Auth refresh에서 `refresh_token_not_found`, `session_expired`, `session_not_found`가 돌아오면 로컬 세션을 정리하고 로그인 화면에 재로그인 안내를 표시합니다. 단일 세션 정책을 활성화하지 않으면 이 안내 흐름은 해당 정책의 세션 대체 이벤트를 만들지 않습니다.

공식 문서: [User sessions](https://supabase.com/docs/guides/auth/sessions)

## 자동 로그인 저장 정책

- 설치 버전: `@supabase/ssr 0.12.5`, `@supabase/supabase-js 2.115.0`. 브라우저 SDK는 쿠키 저장소를 사용하며 인증 세션을 별도 localStorage에 저장하지 않습니다.
- 체크: SDK 기본 400일 쿠키 수명을 유지합니다. 이는 저장 수명일 뿐, Supabase 세션 만료/단일 세션/승인/권한 정책을 연장하지 않습니다.
- 미체크: 인증 청크, 정책 쿠키, 브라우저용 모드 쿠키에서 `Max-Age`/`Expires`를 제거합니다. 탭 이동과 새로고침은 유지되며 일반적인 브라우저 종료 시 삭제됩니다.
- 서버는 Supabase `session_id`에 묶인 HMAC 서명과 HttpOnly 정책 쿠키를 검증합니다. 읽기 가능한 모드 쿠키는 브라우저의 쓰기 옵션 안내용이며 서버의 인증 판단 근거가 아닙니다.
- `AUTH_SESSION_POLICY_SECRET`을 충분히 긴 임의의 서버 전용 값으로 설정하는 것을 권장합니다. 없으면 기존 `SUPABASE_SERVICE_ROLE_KEY` 또는 `SUPABASE_SECRET_KEY`를 사용합니다. 공개 환경변수에 넣지 마세요. 모든 서버 인스턴스의 키가 같아야 하며 키 변경 시 재로그인이 필요합니다.
- 이메일, Google, Apple, Kakao, Naver 로그인에 같은 정책을 적용합니다. OAuth 시작 API가 선택값을 10분 유효한 서명/HttpOnly 세션 쿠키에 보관하고 콜백에서 소비합니다. 콜백 쿼리로 자동 로그인을 활성화하지 않습니다. 동시 OAuth 로그인은 마지막 시작 요청의 선택값을 사용합니다.
- 회원가입의 브라우저 직접 인증은 `/api/auth/session` POST에서 인증 사용자 확인 후 기본 미체크 정책을 발급합니다. 기존 세션과 ID가 일치하는 유효 정책은 보존하지만 이 API로 자동 로그인을 새로 활성화할 수 없습니다.
- 새 정책이 없는 기존 인증 쿠키는 일반 요청에서 정리하고 재로그인을 요구합니다. 로그아웃은 SDK 토큰 정리와 서버 정책 쿠키 삭제를 함께 수행합니다.

### 브라우저 종료의 한계와 수동 검증

브라우저의 "이전 세션 복원", 충돌 복구, 백그라운드 실행은 세션 쿠키를 보존/복원할 수 있습니다. 웹 서버는 브라우저 프로세스의 완전 종료를 신뢰할 수 있게 관찰할 수 없으므로 이 설정에서도 재접속 로그인이 절대 복원되지 않는다고 보장하지 않습니다. 엄격한 보장이 필요하면 관리형 브라우저의 세션 복원 금지 등 별도 운영 정책이 필요합니다.

1. 이메일과 Google/Apple 각각 체크/미체크 로그인 후 인증 쿠키 청크와 정책 쿠키의 수명을 DevTools에서 확인합니다. 정책 쿠키는 HttpOnly여야 합니다.
2. HQ/OWNER/STAFF의 정상 승인 계정과 승인 대기 계정에서 기존 라우팅, 페이지 이동, 새로고침을 확인합니다.
3. 브라우저 세션 복원을 끄고 모든 창과 백그라운드 프로세스를 종료합니다. 다시 열어 미체크는 로그인 화면, 체크는 권한별 화면으로 진입하는지 확인합니다. 세션 복원을 켠 경우는 별도로 기록합니다.
4. 토큰 갱신 이후에도 체크/미체크 쿠키 수명이 유지되는지, 체크 후 미체크 재로그인 시 영속 쿠키가 제거되는지 확인합니다.
5. 모드 쿠키를 `persistent`로 변경해도 미체크 서버 정책이 바뀌지 않는지 확인합니다. 정책 쿠키 삭제/변조 시 보호 페이지와 API 인증이 거부되는지 확인합니다.
6. 로그아웃 후 모든 인증/정책 쿠키 제거, 다시 접속 시 비로그인, 단일 세션 대체 안내, OAuth 취소/실패 및 회원가입/이메일 인증 흐름을 확인합니다.

자동 테스트는 쿠키 삭제를 모사한 종료, 정책 서명, 갱신, 청크 교체, SDK 로그인/로그아웃을 검증합니다. 실제 제공자 인증과 브라우저 프로세스 재시작 테스트를 대체하지 않습니다.
